# Шаблоны оформления блоков приключения (v03)

> Единые шаблоны для `v03/*.md`. Каждый блок (локация, персонаж, сцена, энкаунтер,
> проверка, допрос, слухи и т.д.) оформляется по своему шаблону, чтобы глава была
> единообразной и машинно-читаемой.
>
> Заполняемый блок = то, что кладётся в `v03/*.md`; «Соответствие JSON» = как это
> поле попадает в JSON-source-of-truth.
> `<...>` — заглушка, которую заполняют; `[...]` — опциональный блок (убирают, если не нужен).
>
> **Сборка.** `generators/assemble_v03.py` собирает `v03/*.md` в один `book.typ`,
> `generators/md_to_typst.py` переводит каждый файл в Typst (нативный, без внешних
> пакетов), затем `typst compile --root . publication/v03/book.typ
> publication/v03/book.pdf`. Порядок файлов задан в `assemble_v03.py`:
> `01-chapter-1` → `02-1-B1` → `03-1-B2` → `04-1-B3` → `90-lore` → `91-dottari`
> → `98-bestiarium`. Бестиарий и лор всегда в конце книги.
>
> **Формат.** Исходники v03 — это **Markdown с `:::`-блоками-контейнерами** и
> **обычной markdown-таблицы**, а не raw Typst. Конвертер сам превращает заголовки,
> `:::`-блоки, таблицы и блок «Стат-блок» в элементы PF2e-стиля
> (`#aloud`, `#check-group`, `#answers-group`, `#encounter`, `#pftab`, `#attention`,
> `#note`, `#figure`, `#image`). Ниже — **исходная v03-синтаксиса**, которую надо
> писать в `.md`; как она выглядит в `book.typ`/`book.txt` — по ссылке к каждому блоку.

# 0. Каталог блоков (что есть, что уже сформировано)

Все блоки ниже — **уже реализованы** в конвертере `md_to_typst.py` и собираются в
`book.pdf`. «Формирование» = как блок-контейнер из `.md` превращается в элемент
Typst. Если блока в каталоге нет — его надо добавить в конвертер.

| #  | Блок (исходная v03-синтаксис)               | Что из него (book.typ / book.txt)                           | Формирование                                                      |
|----|---------------------------------------------|-------------------------------------------------------------|-------------------------------------------------------------------|
| —  | `# Глава N. <Имя>` (H1)                     | `#chap-header("N","Имя","")`                                | H1 «Глава N» → шапка главы                                        |
| —  | `## …` / `### …` / `#### …` / `##### …`     | `#chap-header(...)` / `=== …` / `==== …` / `===== …`        | Заголовки 1-го уровня → `#chap-header`; `##..######` → `#h1..#h6` |
| 1  | `::: image [capt;width:..;height:..] … :::` | `#place(top+center, …)[ #figure(image(…), caption: [..]) ]` | `image` → полностраничный `#figure`                               |
| 2  | `::: figure [capt] … :::`                   | `#figure(…)` (полностраничный / inline в `::: block`)       | `figure` → `#figure`                                              |
| 3  | `::: block … :::`                           | `#block(…)` (полностраничный `#place`)                      | `block` → `#block`-обёртка                                        |
| 4  | `::: one-col … :::`                         | `#set page(columns: 1)` (на время блока)                    | `one-col` → выключение 2-колонки                                  |
| 5  | `> …` (цитата)                              | `#aloud[ … ]` (read-aloud)                                  | `>…` → `#aloud`                                                   |
| 6  | `::: aloud [Title] … :::`                   | `#aloud[ … ]`                                               | `aloud` → `#aloud`                                                |
| 7  | `::: attention [Title] … :::`               | `#attention[Title … body]`                                  | `attention` → `#attention`                                        |
| 8  | `::: note [Title] … :::`                    | `#note[Title … body]`                                       | `note` → `#note`                                                  |
| 9  | `::: check … :::`                           | `#check-group(…)`                                           | `check` → `#check-group`                                          |
| 10 | `::: answers [Title] … :::`                 | `#answers-group(…)`                                         | `answers` → `#answers-group`                                      |
| 11 | `::: rumors [dN, Title] … :::`              | `#pftab(…)` (таблица слухов)                                | `rumors` → `#pftab`                                               |
| 12 | `::: encounter [Name] … :::`                | `#encounter((…))` (тонкий, без stat-table)                  | `encounter` → `#encounter`                                        |
| 13 | `#### [PF2e stat-block] …`                  | `#encounter((…))` (полный, с таблицей)                      | stat-block → `#encounter`                                         |
| 14 | markdown-таблица `                          | a                                                           | b                                                                 |`             | `#pftab(…)`                      | table → `#pftab` |
| 15 | `::: pftab [Title] … :::`                   | `#pftab(…)` (явная обёртка таблицы)                         | `pftab` → `#pftab`                                                |
| 16 | `[text](https://…)` (ссылка)                | `#link("…")[text]`                                          | link → `#link`                                                    |

> **Две формы энкаунтера.** `#### [PF2e stat-block]` (§4) — **полный** stat-block
> (таблица параметров + список способностей), конвертер строит `#encounter` с
> таблицей. `::: encounter [Name]` (§11) — **тонкий** `#encounter` только с
> названием и списком способностей, **без** stat-table — для ad-hoc блоков
> способностей, где нет полного стат-блока (напр. способности Фальконе в сцене B3).

# 1. Шаблон локации

> Все секции ниже идут **в одинаковом порядке**. Пропущенную опциональную секцию
> удаляют, не оставляют пустой.

## 1.1. Структура блока (порядок секций)

```
### M.N.O <Название локации> (<Имя на языке лора / англ.>)

::: image [Название; width:..; height:..]
![<Название>](<путь к карте>)
:::

#### Зачитать при первом входе в локацию
::: aloud [Зачитать при входе]
<3–6 предложений «живого» описания — то, что Мастер читает игрокам голосом.
 Атмосфера + первое, что видят/слышат/чувствуют. Без ссылок на улики.>
:::

#### Атмосфера
<Плотный абзац: что это за место, куда оно вписывается в город/таверну,
 какой контраст создаёт. Ссылка на parent (в какую родительскую зону входит).>

#### Наблюдения
::: check
<Название проверки>
[<Характеристика>, <СЛ N>]
success: <что видно при успехе>
critical_success: <что видно при критическом успехе>
failure: <что видно при провале>
:::

#### Входы и выходы
- **Вход:** <откуда приходят> (ссылка на локацию/дверь).
- **Выход:** <куда ведут> → <ID/название следующей локации>.
- **Выход (условный):** <только если <условие>>.
- **Секретный вход/выход:** <если есть>.

#### Куда ведёт по расследованию
- **Зацепка → действие → результат → следующая локация** (одна строка на цепочку).
- **Зацепка:** <что узнали/нашли> → **действие:** <что делают> → **результат:** <что получают/узнают> → **следующая локация:** <куда идут>.

#### Зацепки
- **<Название зацепки>** — <что это>. Условие: <как получить>.
- **<Название зацепки>** — <что это>. Условие: <как получить>.

#### Улики
- **<Название улики>** (ID: `evidence_id`) — <что это, что она говорит>. Способ обнаружения: <проверка/обыск> (СЛ <N>).
- **Ложная зацепка (красная сельдь):** <что сбивает, но не блокирует>.

#### Скрытое (при обыске/наблюдении)
- **<Название скрытой детали>** — <что найдут>. Улика: `evidence_id`. Условие: <обыск/наблюдение> (СЛ <N>).

#### NPC
- **<Имя (Роль)>** — <кто, что здесь делает>. См. §2 (персонажи) / [раздел персонажей].

#### История и архитектура
- <Лорный факт про место>.
- <Лорный факт про место>.

#### [События]  (опционально — если в локации есть сцена/энкаунтер)
##### Сцена: <название>
- **Как это работает.** <что происходит, условия>.
- **Атмосфера.** <как это ощущается>.
- **Улики/намёки.** <что заметят при проверке (СЛ N); при критическом успехе — что ещё>.
- **Связь с расследованием.** <как это вписывается в цепочку>.
- **Последствие.** успех → <что получают>; провал → <что происходит>.

#### [Боевая сцена]  (опционально — см. шаблон энкаунтера §4)

#### GM knows
::: note [GM knows]
- <Что знает Мастер, но НЕ игрок>: тайна/секрет локации, что делает NPC, что случится при <условии>.
- **Критическая улика:** <какая улика здесь обязательна и нельзя её потерять из-за одного провала> → <как гарантировать, что игроки её всё равно получат>.
:::
```

## 1.2. Поле-к-полю: v03-блок ↔ JSON

| Секция в блоке                   | JSON-поле (locations/*.json)                      | Комментарий                                               |
|----------------------------------|---------------------------------------------------|-----------------------------------------------------------|
| Заголовок / Имя                  | `name`                                            | Имя + лор-имя в скобках                                   |
| (заголовок, тип)                 | `type` (`context`/`gameplay`)                     | Определяют ли они сцену или только фон                    |
| (заголовок, родитель)            | `parent_location`                                 | В какую зону входит                                       |
| Зачитать при входе (`::: aloud`) | — (только для Мастера, не в JSON)                 | Голосовой заход → `#aloud`                                |
| Атмосфера                        | `appearance` + `description`                      | Визуал + «что это за место»                               |
| Наблюдения (`::: check`)         | `observation` (`{skill, dc, success, failure}`)   | Что видно при осмотре/проверке (с DC/СЛ) → `#check-group` |
| Входы и выходы                   | — (нет поля; связки — в `location_graph.mermaid`) | Связи; поле `entrances`/`exits` — добавить                |
| Куда ведёт по расследованию      | — (нет поля)                                      | Цепочка зацепка→действие→результат→локация                |
| Зацепки                          | `clues` (ссылки)                                  | Что дают игроки в расследовании                           |
| Улики                            | `clues` + `hidden[].evidence`                     | Primary/secondary/false/accident                          |
| Скрытое                          | `hidden[]` (`{description, evidence, check}`)     | Что найдут при обыске/наблюдении (`check` = DC)           |
| NPC                              | `characters[]`                                    | Кто здесь                                                 |
| История и архитектура            | — (лор, не в JSON)                                | Фон                                                       |
| События                          | `important_events[]`                              | Сцены/события в локации                                   |
| (атмосфера: smell/sound/feeling) | `senses` (`{smell, sound, feeling}`)              | Сенсорное описание                                        |

> **Унификация:** в `locations.schema.json` уже добавлено поле `observation`
> (`{skill, dc, success, failure}`) и `check` у `hidden[]` — так DC/СЛ попадает
> в JSON и совпадает с v03-блоком. Ещё нет полей `entrances`/`exits`/`leads_to`
> (цепочка зацепка→действие→результат→локация) — связки пока только в
> `location_graph.mermaid`; добавить их при следующем проходе.

# 2. Шаблон персонажа (NPC)

> Два источника стиля: блок NPC в v03-главе (раздел «Основные персонажи») и JSON

## 2.1. Структура блока (порядок секций)

```
### <Роль> — <Имя> (d6=<N>)
![Портрет <Имя>](<путь к портрету>)

#### Идентификация
- **Имя:** <полное имя>
- **Прозвище:** <если есть>
- **Роль:** <занимаемая в сцене>
- **Раса:** <раса>
- **Мировоззрение:** <PF2e alignment>
- **Статус:** main_npc / context_npc / ghost
- **Может ли быть жертвой:** true / false

#### Описание
<2–4 предложения «кто это» — профессия, характер, роль в истории.>

#### Внешний вид и черты лица
<Лицо, телосложение, особые приметы. Без ссылок на улики — только то, что видно.>

#### Одежда и детали
<Что одет/носит; заметные предметы.>

#### Поведение и шлейф восприятия
<Как себя ведёт, как реагирует, что заметят при наблюдении.>

#### Речь
<Как говорит: регистр, темп, громкость, клички, жесты.
 По уровням L1–L4 — см. ниже (не заменяет сами ответы, описывает ПОДАЧУ).>

#### Профессия
- <должность/занятие>
- <доп. роль/тайная роль, если раскрывается>

#### Скрывает
- **[big]** <большая тайна>.
- **[small]** <малая тайна>.
- **Кто знает** (known_by): <ID персонажей, знающих о тайне>.

#### Хочет
- <цель 1>
- <цель 2>

#### Боится
- <страх 1>
- <страх 2>

#### Отношения
- **<Имя (Роль)>** — <тип связи + что это значит>.
- **<Имя (Роль)>** — <тип связи + что это знает/не знает>.

#### [PF2e stat-block]  (опционально — если персонаж/ NPC участвует в бою или нужен для игры)
> См. §4 (шаблон энкаунтера / стат-блока). Единый стандарт: 20-строчная таблица параметров (порядок из §4.1)
> + отдельный список «Способности». НЕ дублировать «Способности» в таблицу; НЕ сжимать 6 характеристик в одну
> строку; НЕ использовать `Тип`/`Сопротивления`/`Характеристики`/`Снаряжение` вместо стандартных строк.

#### GM knows
::: note [GM knows]
- **Тайна:** <что Мастер знает, но игрок — нет>.
- **Реакции:** найден <улика/секрет> → <как реагирует: меняет показания / угрожает / атакует>.
- **При обнаружении:** если застали тайком → <что делает>.
- **При раскрытии тайны:** <угрожает / признаётся / убегает / атакует>.
- **Ложные убеждения:** <во что верит, но неверно> (confidence: high/medium/low).
:::
```

# 4. Шаблон энкаунтера / бой (внутри локации)

> Единый шаблон для `#### [PF2e stat-block]`-блока, который конвертер `md_to_typst.py`
> разбирает в `#encounter((…))` (полный stat-block с таблицей параметров + список
> способностей). Заголовок над блоком задаёт имя и d6 (`## Стат-блок: <Имя> —
> <Роль> (d6=N)`). Конвертер идёт по **именам строк** таблицы, не по порядку.

## 4.1. Структура блока (порядок строк, строго как ниже)

> Порядок строк таблицы — **единый стандарт**. Пропущенную строку удаляют целиком
> (не оставляют пустой), но **никогда не меняют порядок и не переименовывают**.
> Конвертер не «узнаёт» строки по порядку, а по имени — поэтому переименование
> (напр. `Тип` вместо `Раса`, `Сопротивления` вместо `Роль`) или пропуск строк
> даёт в PDF неполную/некорректную таблицу.

```
## Стат-блок: <Имя> — <Роль> (d6=<N>)

### [PF2e stat-block]

### <Имя / Название>

![Портрет](<путь>)

| Параметр | Значение |
|----------|----------|
| **Уровень**       | <N> |
| **Мировоззрение** | <LE/N…> |
| **Размер**        | <Средний> |
| **Тип**           | <Гуманоид (Человек)> |
| **Роль**          | <Контролёр / офицер> |
| **Восприятие**    | +N; <ночное/сумеречное зрение, нюх и т.п.> |
| **Языки**         | <Общий, …> |
| **Навыки**        | <Атлетика +N, Запугивание +N, …> |
| **Сила**          | +N |
| **Ловкость**      | +N |
| **Телосложение**  | +N |
| **Интеллект**     | +N |
| **Мудрость**      | +N |
| **Харизма**       | +N |
| **Предметы**      | <длинный меч, кольчуга, тяжёлый щит, …> |
| **AC**            | <N (… с щитом)> |
| **HP**            | <N> |
| **Скорость**      | <N футов> |
| **Спасброски**    | <Стойкость +N, Реакция +N, Воля +N> |
| **Ближний бой**   | <оружие +N [мод] (урон; трейты)> |
| **Ближний бой**   | <2-й оружей — повторная строка «Ближний бой»> |
| **Дальний бой**   | <оружие +N [мод] (урон; трейты)> |

**Способности:**

- **<Название> (<англ.>)** `[one-action]` <трейты> — <описание>.
- **<Название> (<англ.>)** `[reaction]` — <описание>.
- **<Название> (<англ.>)** `[free-action]` — <описание>.
```

## 4.2. Правила оформления (что НЕ делать)

- **Одна строка на параметр.** Не смешивать характеристики в одну строку
  `Характеристики | Сил N, Лов N, …` — каждая из 6 (Сила/Ловкость/Телосложение/
  Интеллект/Мудрость/Харизма) — **отдельная** строка таблицы (конвертер идёт по
  имени строки; слиянная строка теряется).
- **Повторные строки «Ближний бой» / «Дальний бой».** Если у существа 2+ оружия в
  одной категории — каждая атака — **своя** строка `Ближний бой` / `Дальний бой`
  (конвертер `parse_table` сохраняет дубли-ключи как список и выдаёт по строке на
  каждое значение). НЕ сжимать 2 меча в одну ячейку через запятую.
- **Не выносить «Способности» в таблицу.** `Способности` — это **отдельный список**
  под таблицей, а НЕ строка таблицы. В табличном виде `Способности` появляется
  только как строка с **параметром** (напр. `Spell DC 25; Spell Attack +17`) — и
  это НЕ список способностей.
- **Имя/уровень — в заголовке, а не в таблице.** `(d6=N)` в заголовке — это **ID
  d6**, НЕ уровень персонажа; уровень берётся из строки `Уровень` таблицы.
- **Не использовать** `Тип`, `Сопротивления`, `Характеристики`, `Снаряжение`,
  `Специальные способности` вместо стандартных строк. Если у существа нет
  класса/роли — оставляют строку `Класс`/`Роль`, а значение описывают (напр.
  `Класс | — (нежить)`), а не убирают строку и не ставят `Тип`.
- **Обрыв по переносу строки.** Каждая способность/параметр — **одна** логическая
  строка. Если в markdown способность обрывается на полуслове из-за переноса (`… отбрасывает на 10` / новая строка
  `футов.`), это **баг источника**: конвертер
  не сливает обрыв — нужно либо писать одной строкой, либо продолжать строку без
  переноса. Продолжение, начинающееся с `-` (напр. `- **Название**:`), — это **новая** способность.
- **Иконки экономики действий** в способностях: `[one-action]` → `#A`,
  `[two-actions]` → `#AA`, `[reaction]` → `#R`, `[free-action]` → `#F`. Конвертер
  сам подбирает иконку по маркеру в `[...]` (или по `(reaction)`/`[reaction]`).

# 6. Блоки-контейнеры `:::` (справочник v03)

Все `:::`-блоки закрываются **голым** `:::`. Заголовок блока задаётся в квадратных
скобках после имени (`::: pftab [Заголовок]`, `::: check`, `::: rumors [d10, …]`
и т.д.) или в теле блока (для `::: check` — первая непустая строка без `[…]; для
`::: answers` — первая строка до `**Q:**`).

## 6.1. `::: image [caption;width:..;height:..] … :::`

Полностраничная `#figure`-карта/локация. Тело — одна markdown-картинка
`![capt](path.png)`. `width`/`height` из spec (напр. `width:100%;height:auto`,
`width:auto;height:90%`); путь к `.png` сохраняется raw (конвертер не трогает
точки в пути). См. §0 строку 1.

## 6.2. `::: figure [caption] … :::`

Полностраничная `#figure` (как `::: image`, но caption из spec, alt из картинки).
Внутри `::: block` рендерится inline (4-space indent), а не как `#place`. См. §0 строку 2.

## 6.3. `::: block … :::`

Полностраничная `#block`-обёртка (`#place`): всё содержимое (включая вложенные
`::: figure`, заголовки, прозу) рендерится целиком, блок закрывается только **своим** `:::` (вложенные `:::` не
закрывают). См. §0 строку 3.

## 6.4. `::: one-col … :::`

На время блока `#set page(columns: 1)` — выключение 2-колонки. Вложенные `:::
pftab`/`::: figure`/`::: answers` внутри `::: one-col` остаются в one-col. См. §0 строку 4.

## 6.5. `::: check … :::`

Проверки. Тело:

```
::: check
<вводная строка (опц. — заголовок группы)>

[<Характеристика>, <СЛ N>]
critical_success: <текст>
success: <текст>
failure: <текст>
critical_failure: <текст>

[<Характеристика2>, <СЛ N2>]
success: <текст>
:::
```

- Каждая строка `[Харак; СЛ]` (или `[Харак, СЛ]`, или `[Харак]` без DC) — новая `check(…)`.
- Уровень `critical_success`/`success`/`failure`/`critical_failure` — именованный аргумент.
- Перенос строки (без `:`) присоединяется к предыдущему уровню.
- Вывод: `#check-group( [вводная], check(…), check(…) )`. См. §0 строку 9.

## 6.6. `::: answers [Title] … :::`

Допрос/ответы NPC по уровню отношения. Тело:

```
::: answers
<заголовок (одна строка, напр. «Вопросы к лейтинанту Фальконе»)>

**Q:** «<вопрос>»
hostile: <ответ>
unfriendly: <ответ>
indifferent: <ответ>
friendly: <ответ>
helpful: <ответ>

**Q:** «<вопрос 2>»
…
:::
```

- Вывод: `#answers-group( [заголовок], answers(q: […], hostile: […], …), … )`.
- Уровни отношения: `hostile`, `unfriendly`, `indifferent`, `friendly`, `helpful`
  (в любом порядке; конвертер выводит те, что заданы). См. §0 строку 10.

## 6.7. `::: rumors [dN, Title] … :::`

Таблица слухов. Title может нести кубик (`::: rumors [d10, Слухи на мосту]`).
Тело — строки `rumor: N | <текст> | <источник> | <улика/событие>`. Вывод:
`#pftab([Title], columns: (…), [dN], [Слух], [Источник], [Улика/событие], …)`.
См. §0 строку 11.

## 6.8. `::: encounter [Name] … :::`

Тонкий `#encounter((…))` без stat-table (только name + type + traits + список
способностей). Тело — список способностей (может начинаться с `**Способности:**`).
Каждая строка `- **Название** [one-action] …` → одна detail-строка `#encounter`
с иконкой (`#A`/`#AA`/`#F`/`#R`). Для ad-hoc блоков способностей без полного
stat-блока (напр. способности Фальконе в сцене B3). См. §0 строку 12.

## 6.9. markdown-таблица → `#pftab`

Обычная markdown-таблица `| a | b |` автоматически рендерится как `#pftab`.
Заголовок таблицы берётся из контекста (ближайший заголовок) или из первого
header-cell. Диалоговые таблицы (вопрос/ответ, вопрос-по-отношению) рендерятся
в **одну** колонку (full-width), чтобы не разрывать реплики. См. §0 строку 14.

## 6.10. `::: pftab [Title] … :::`

Явная обёртка `#pftab` вокруг markdown-таблицы (если надо задать заголовок явно).
См. §0 строку 15.

## 6.11. `> …` (цитата) → `#aloud`

Блок-цитата (`>…`) рендерится как `#aloud[ … ]` (read-aloud). См. §0 строку 5.

## 6.12. `::: attention [Title] … :::` / `::: note [Title] … :::`

- `::: attention` → `#attention[Title … body]` (акцент-блок).
- `::: note` → `#note[Title … body]` (блок для GM/примечаний).
  См. §0 строки 7, 8.

## 6.13. `[text](https://…)` → `#link`

Markdown-ссылка `[text](url)` рендерится как `#link("url")[text]`. См. §0 строку 16.
